# Drill-completion validation via Monkeytype tagging

Checking whether the impact-score model in [0002-drill-design.md](0002-drill-design.md) produces real improvement requires per-bigram latency measured before and after a *genuine* drill completion, not just any keylog timestamp — the keylogger records every keystroke typed into Monkeytype regardless of mode or content. We tag drill completions in Monkeytype via an extended keylogger userscript, and let the existing results sync — which already reads `tags` — close the loop with no new backend write path.

## Mechanism

1. The backend gains a lightweight `GET` endpoint exposing the category and bigrams of the most recently generated drill (`/drills/{name}` only serves raw pipe-delimited text today).
2. `monkeytype-keylogger.user.js` fetches it and loads it by driving Monkeytype's own "custom" mode → "change" text popup: filling its textarea and submitting its form, the same as a person pasting text by hand. (`customText` / `customTextSettings` in localStorage turned out to be Monkeytype's *saved-presets* library, not the live/active test state — confirmed by testing that writing them and reloading did nothing; the popup's own form submission is the only thing that actually applies new text.) The pipe delimiter is a one-time setting in Monkeytype itself, not something applied per drill.
3. Because `/api/dashboard` regenerates the drill files from live DB state on every call, the bigram set behind a category is a moving target — the file the userscript fetches for this session's `drill-sfb` won't necessarily match what `drill_practice_sfb.txt` contains by the time a report runs later. The script therefore embeds the fetched manifest (category, bigram list, fetch timestamp) into the same JSON envelope it already saves for that keylog session, so later reporting reads what was *actually* served at the time, not whatever the server currently happens to be regenerating.
4. On test completion — detected via the `data-result-id` / `data-active-tag-ids` attributes Monkeytype's results screen already sets on its tag-editor button — the script applies a per-category tag (`drill-sfb`, `drill-row_skip`, `drill-awkward_roll`, `drill-lsb`, `drill-overall`) by driving the real tag-editor UI, the same way a person would. The tag identifies *which category* a completion belongs to; it's the envelope's embedded manifest from step 3 that identifies *which bigrams*, matched back to this result by the same timestamp-window join `attempts` already uses.
5. Tags are created once, by hand, in Monkeytype's UI before the script can reference them by ID — that's a one-time setup for the tag's identity, independent of and unaffected by the drill content rehydrating on every request.
6. `fetch_monkeytype_results.py`'s existing sync already reads `tags` on every pull — no new backend write endpoint or auth model is needed; tagging on Monkeytype's own servers is enough.

## Reporting

The category tag is only used to find genuine drill completions in `results` — it isn't the unit of analysis, since there's no fixed "the SFB bigrams" to compare against once the drill regenerates from live DB state on every request. For each tagged completion, the target of the before/after comparison is every individual bigram in that session's embedded manifest (step 3): a bigram's keylog median latency before vs. after that specific completion is computed using the dashboard's existing `load_bigram_rows_db`. A bigram that recurs across multiple tagged completions over time (e.g. drilled again in next week's `drill-sfb` session) produces one before/after instance per occurrence, rolled up per bigram in the report. This surfaces as a new passive insight on the dashboard, alongside `compute_insights` / `compute_action_plan`. It does not feed back into the impact-score formula automatically — a human judges whether the theory holds before drill generation changes because of it.

## Considered alternatives

- **`mode = custom` alone, no tagging** — fully automatic, no new UI automation needed, but any unrelated custom-text paste (or a stale prior drill) would be misattributed as validating the current bigram set.
- **Reusing Monkeytype's internal `updateTags` call directly**, via `@grant unsafeWindow` to reach its Firebase Bearer token and page-internal request path — more seamless once working, but couples the script to private, minified, unversioned internals Monkeytype owes no stability to; breakage would be silent.
- **A single generic `drill` tag** — less one-time setup (one tag instead of five), but only ever confirms "some drilling happened," not which category drove any observed improvement.
- **Correlating against real Monkeytype test WPM trend** instead of per-bigram keylog latency — a more direct measure of the thing ultimately cared about, but needs its own session-tagging discipline to control confounds (one drill category active per session, no other practice mixed in) and is much noisier to attribute. Per-bigram latency comparison already has the infrastructure to compute today.
- **Auto-tuning the impact-score formula from validation deltas** — would turn this into a self-tuning system, but the underlying model is itself unproven; letting it tune itself off real-world deltas that are still noisy and only partially deconfounded risked compounding a wrong assumption silently.
- **Re-reading the current drill file at report time instead of embedding a manifest** — simpler, no envelope changes needed, but wrong: `/api/dashboard` regenerates drill files from live DB state on every call, so the bigram set behind a category tag at report time can differ from what was actually served when that completion happened.
- **Writing `customText` / `customTextSettings` to localStorage, then reloading** — the original design here, before live testing showed it does nothing. Those keys are Monkeytype's saved-presets library (the "saved texts" picker), not the state that determines what a freshly opened custom test actually loads; that only gets set by the popup's own form submission. Driving the popup directly is both correct and simpler — it also removes the reload, which stops it from interfering with any other Monkeytype tab open at the same time.
