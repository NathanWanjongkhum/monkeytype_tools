# Drill phrase length tracks repeat count inversely

`generate_drill_list.py` builds one drill entry per targeted bigram: a phrase of dictionary words containing the bigram, repeated `repeat` times back-to-back. `repeat` was already weighted by `weight = median / fastest_median` (how much slower this bigram is than the fastest one in the pool) — slower bigrams get more repeats. Phrase length (`WORDS_PER_BIGRAM`) was a flat constant (4) applied to every entry regardless of `weight`.

We now derive phrase length from the same `weight`, inversely: `words_n = clamp(1, 4, round(4 / weight))`. The worst bigram in the pool collapses toward a single word repeated up to 15x — a tight, narrow, high-frequency motor loop, since the priority for a badly-lagging bigram is grooving that exact keystroke transition, not diluting the loop with 3 other words of unpredictable length. A bigram that barely qualified (`weight` near 1) gets the full 4-word phrase repeated only 3x — closer to a context check than rote drilling, since it doesn't need concentrated repetition, just confirmation that it's fast across different surrounding letters.

The rejected alternative was leaving phrase length flat and only scaling `repeat`: the worry was that narrow, single-word rote drilling risks a motion that's fast in isolation but doesn't transfer back to real typing. That's a real risk in a one-shot drill, but not here, because drills regenerate from fresh typing data on every run — as a bigram's `weight` drops from actually getting faster, the *next* generated drill automatically widens its phrase and shortens its repeat count. A bigram graduates from tight rote loop toward varied context on its own; the narrow treatment is where a bad bigram starts, not a permanent state.
