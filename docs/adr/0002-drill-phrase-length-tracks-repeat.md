# Drill generation: weighted phrase/repeat, capped to a test-sized word budget

`generate_drill_list.py` turns your slowest qualifying bigrams (from the same "Slowest bigrams" pool as the dashboard) into a Monkeytype-pasteable custom word list: one drill entry per targeted bigram, a phrase of real dictionary words containing that bigram, repeated `repeat` times back-to-back and joined with `|`. Three decisions shape what that pasted list looks like: how many bigrams are even candidates, how each candidate's phrase length and repeat count are chosen, and — the part that was missing until now — how many of those candidates actually make it into one generated test.

`TARGET_BIGRAMS_N` (20) sets the *candidate* pool: the 20 slowest qualifying bigrams, sorted worst-first, same ordering the dashboard uses. Within that pool, both `repeat` and phrase length (`words_n`) are derived from `weight = median / fastest_median` — how much slower this bigram is than the fastest one in the pool — but inversely: `repeat = clamp(3, 15, round(3 * weight))` while `words_n = clamp(1, 4, round(4 / weight))`. The worst bigram in the pool collapses toward a single word repeated up to 15x — a tight, narrow, high-frequency motor loop, since the priority for a badly-lagging bigram is grooving that exact keystroke transition, not diluting the loop with 3 other words of unpredictable length. A bigram that barely qualified (`weight` near 1) gets the full 4-word phrase repeated only 3x — closer to a context check than rote drilling, since it doesn't need concentrated repetition, just confirmation that it's fast across different surrounding letters. Drills regenerate from fresh typing data on every run, so a bigram graduates from tight rote loop toward varied context on its own as it gets faster; the narrow treatment is where a bad bigram starts, not a permanent state. The rejected alternative here was leaving phrase length flat and only scaling `repeat`: narrow, single-word rote drilling risks a motion that's fast in isolation but doesn't transfer back to real typing, but that risk is contained by the same regeneration-from-fresh-data property — it isn't a one-shot drill.

Left unchecked, though, `TARGET_BIGRAMS_N` candidates each getting their own independently-weighted `repeat * words_n` compounds into a paste far bigger than one test: 20 entries at up to 4 words * 15 repeats each can reach hundreds of words, and even at typical weights routinely landed around 150-200 words for a single generated test — several times longer than the run the constants were tuned for. So `build_drill_entries` now walks the candidate pool worst-first and stops adding entries once a `TARGET_WORDS_N` (50) word budget is spent, computing each entry's `repeat`/`words_n` exactly as before but clipping the boundary entry's `repeat` down (never below 1) to fit the remaining budget instead of dropping it outright. `TARGET_BIGRAMS_N` still bounds the candidate pool, but `TARGET_WORDS_N` is what actually determines how many bigrams show up in a given generated list — commonly far fewer than 20, concentrated on the worst offenders. The rejected alternative was scaling every candidate's `repeat` down by a single global factor to hit the budget exactly: that would have kept all 20 bigrams present but diluted the worst ones down to only a few repeats each, undoing the tight-rote-loop treatment they need. Stopping early instead means only the pool's worst few actually appear in any one test, which fits how the pool is regenerated anyway — the ones that don't make the cut this run are exactly the ones already fast enough to wait, and they'll surface once something worse graduates out. The same budget applies per category in `build_category_drills`/`generate_category_drills` (`CATEGORY_TARGET_BIGRAMS_N` only shrinks that category's candidate pool to 8), so each category's drill file is independently capped to a test-sized paste too.
